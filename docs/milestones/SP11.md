## Goal

A stranger on a phone, with no login, loads one URL and sees two numbers: events processed and dead-letter depth. That page is why the Compose runtime is a demo and not a screenshot. Everything that writes stays behind Cloudflare Access, on a different hostname.

Two rules shape it: a login wall is not a demo, and a write path does not belong on a public hostname.

## Part 1: The status service

### compose/status/

#### 1. `compose/status/index.ts`

**File Type:** `typescript`
**File Name:** `compose/status/index.ts`

| Behavior | Set To |
|---|---|
| the clients | a Redis client at `REDIS_URL`, and a Postgres pool from `PG_HOST`, `PG_USER`, `PG_DB`, and the password read from `PG_PASSWORD_FILE` |
| a method that is not GET | answer `405` and stop |
| the two numbers | `SELECT count(*)::int AS n FROM events`, and `xLen("events-dead")`, in one `Promise.all` |
| the response | `200`, `content-type` `application/json`, and a body of `{ processed, deadLetterDepth }`, with `processed` from the count and `deadLetterDepth` from the stream length |
| the port | `8080` |

**Docs:** [Node HTTP server](https://nodejs.org/api/http.html) · [XLEN](https://redis.io/docs/latest/commands/xlen/) · [node-postgres](https://node-postgres.com/)

Read-only by design, not by policy: the service has no route that writes, so there is nothing to protect behind a login. That is a stronger guarantee than a rule that says "do not call the write route".

## Part 2: The tunnel

#### 3. Two services and one token

Add to `compose.yaml`:

| Service | Set To |
|---|---|
| `status` | `build: ./compose/status`, `ports` `["127.0.0.1:8080:8080"]`, `REDIS_URL`, `PG_HOST` = `postgres`, `PG_USER` = `postgres`, `PG_DB` = `events`, `PG_PASSWORD_FILE` = `/run/secrets/pg_password`, `depends_on: [redis, postgres]`, the `pg_password` secret, `restart: unless-stopped` |
| `cloudflared` | `image: cloudflare/cloudflared:latest`, `command` `tunnel --no-autoupdate run`, `environment` `TUNNEL_TOKEN: ${TUNNEL_TOKEN}`, `depends_on: [status, ingest]`, `restart: unless-stopped` |

**Docs:** [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/) · [Cloudflare Access](https://developers.cloudflare.com/cloudflare-one/policies/access/) · [Rate limiting rules](https://developers.cloudflare.com/waf/rate-limiting-rules/)

Both services publish on `127.0.0.1` only, and `cloudflared` publishes nothing: it reaches the two containers over the Compose network by service name. That is the whole exposure story. SP10's step 6 fails if either port line loses its loopback prefix, and it is re-run by this milestone's check.

The token comes from the Cloudflare Zero Trust dashboard and lives in the shell that starts Compose, never in a file in this repository. A token in git is a tunnel anyone can open. Under Podman the value still arrives as an environment variable for the `cloudflared` service, set in the shell that runs `podman compose up`; the compose file reads `${TUNNEL_TOKEN}` and never holds the token itself.

### How to see your results


The check prints one row per step, in the order the parts appear, and a step is green only when its file is in place and every assertion in it passes. A red row prints the reason underneath it, naming the file, the value, or the attribute that is wrong. CI prints the same rows in the job summary, so the local run and the remote run read identically.


**Locally:** `bash .github/scripts/check-local.sh`. **On the pull request:** **Actions**, newest run, **Summary**.

| Step | Checks |
|---|---|
| 1 (status) | GET only, `405` otherwise, the count query, the dead-letter length, the JSON content type, and the two field names |
| 2 (tunnel) | the status service, its loopback publish, the cloudflared service, the official image, the token from the environment, and the start order |

Reading a failure:

- **Step 1 ❌ on `405`**: the service has to refuse a method it does not serve. A status page that answers a POST is a status page that can be probed.
- **Step 2 ❌ on `TUNNEL_TOKEN`**: the compose file must read the token from the environment. Do not add a file for it.

## Done when (dashboard work, then one page)

One prerequisite, and it is the only thing in this guide that costs money outside AWS: both hostnames need a domain whose DNS is on Cloudflare. A free `*.trycloudflare.com` quick tunnel exists, but it hands out a new random hostname every time, so fixed names, an Access application and a rate-limit rule all need a domain you own.

The dashboard also moves between Cloudflare releases, so each step below names the feature to look for, and the breadcrumb beside it is only where the current release keeps that feature: if a screen is not where this says, search the Zero Trust interface for the feature name. Three settings live in the dashboard, and the check cannot read them, so these are yours.

In **Zero Trust → Networks → Tunnels**, make a tunnel for the Kamrui H1, the machine you are on, and copy its token into the shell that runs Compose:

```bash
export TUNNEL_TOKEN='the-token-from-the-dashboard'
podman compose up -d --build
podman compose ps
```

Expected: `cloudflared` is running next to the other five.

In the tunnel's **Public Hostnames**, add two:

| Hostname | Service | Access |
|---|---|---|
| `status.YOUR-DOMAIN` | `http://status:8080` | public, plus a rate-limiting rule |
| `ingest.YOUR-DOMAIN` | `http://ingest:8081` | covered by a Cloudflare Access application |

Then add a rate-limiting rule for the path `/` in **Security → WAF**. The Free plan cannot match a hostname, so the rule covers every hostname in the zone, ingest included; it allows one rule, it matches on the request path only (no hostname, header or cookie matching), and the counting window is 10 seconds over the whole zone. One page load is a couple of requests, so set the rate above what a person needs — 20 requests per 10 seconds per IP on `/` is a workable start — then load the page once to confirm the rule does not block you.

**The Access application, in four steps.** The write path is only protected once that application exists, and no check can see the dashboard:

1. **Zero Trust → Access → Applications → Add an application → Self-hosted**, with `ingest.YOUR-DOMAIN` as the public hostname. One application, one hostname.
2. Add a policy to it that allows your own address: an `Allow` policy with an `Emails` selector. That is the login wall the status page deliberately does not have.
3. **Zero Trust → Access → Service Auth → Service tokens** creates a client id and secret for scripts. Export both in the shell that runs `curl`:

```bash
export CF_ACCESS_CLIENT_ID='the-client-id'
export CF_ACCESS_CLIENT_SECRET='the-client-secret'
```

4. Go back to the application and add a **second policy**, with the action set to **Service Auth** and the token from step 3 as its only selector. Cloudflare's service-token page is direct about why: "Make sure to set the policy action to Service Auth; otherwise, Access will prompt for an identity provider login." With the `Allow` policy alone, the `curl` below is an anonymous visitor, and Access answers it with the login redirect instead of `202`.

A service token is how a command gets through Access without a browser, and every request from a script then carries two headers:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://ingest.YOUR-DOMAIN/ \
  -H "CF-Access-Client-Id: $CF_ACCESS_CLIENT_ID" \
  -H "CF-Access-Client-Secret: $CF_ACCESS_CLIENT_SECRET" \
  -H 'content-type: application/json' -d '{"idempotencyKey":"sp11-1"}'
```

Expected: `202`, where the same request without the headers got `302` or `403`. The secret is a password for the write path: keep it in the shell, never in the repository.

Prove the split from a device that is not signed in to Cloudflare: a phone on mobile data, or a private window.

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://status.YOUR-DOMAIN/
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://ingest.YOUR-DOMAIN/ \
  -H 'content-type: application/json' -d '{"idempotencyKey":"sp11-1"}'
```

Expected: `200` from the status page, and `302` or `403` from the ingest route, because Access sends an unauthenticated visitor to a login page. A `202` from the second command means the write path is public, and that is the one outcome this milestone exists to prevent.

Then submit a signed-in event and load the status page again: the processed count moves by one.
