**The money stops here.** The destroy is the last thing that touches AWS, and it happens the same day the evidence is captured.

It also has a hard end date: the free plan ends on 2026-11-05. AWS suspends an account whose plan ends and keeps its data for 90 days, and upgrading to a paid plan inside that window reopens the account and its resources. This project still destroys the stack and keeps the evidence instead of paying, so the date is a decision rather than a wall: a destroy left unconfirmed after it would need an upgrade before anyone could confirm it, which is the cost this milestone avoids.

## Goal

Two artifacts and one action. The action is the destroy. The artifacts are a script that asks AWS whether anything is left, and an index that says what the evidence folder holds and why each file matters.

A destroy that failed halfway is the expensive mistake in this project: the log says it finished, one resource is still there, and it bills until somebody notices.

## Part 1: The check

#### 1. `scripts/check-destroyed.sh`

**File Type:** `bash`
**File Name:** `scripts/check-destroyed.sh`

| Piece | Set To |
|---|---|
| strict mode | `set -euo pipefail` |
| the prefix | `PREFIX=${1:-serverless-pipeline}` |
| the region | `REGION=${AWS_REGION:-${AWS_DEFAULT_REGION:-us-east-1}}`, passed as `--region` on every call |
| the preflight | `aws --region "$REGION" sts get-caller-identity`; if it fails, say nothing was checked and `exit 2` |
| each answer | `if ! fns=$(aws ... ); then ...; exit 2; fi`, then pass `$fns` to the helper, so a failed call cannot print a green line |
| a helper | a function that takes a label and a found value, prints ✅ when the value is empty, prints ❌ and the value when it is not, and sets a flag |
| the four checks | Lambda functions with `--query "Functions[?starts_with(FunctionName,'$PREFIX')].FunctionName"`, SQS queues with `--queue-name-prefix "$PREFIX"`, DynamoDB tables with a `starts_with` filter on the name, and buckets with a `starts_with` filter on `Name` |
| the ending | when the flag is set, print the hint and `exit 1`; otherwise print one success line and exit `0` |

**Docs:** [list-functions](https://docs.aws.amazon.com/cli/latest/reference/lambda/list-functions.html) · [list-queues](https://docs.aws.amazon.com/cli/latest/reference/sqs/list-queues.html) · [list-tables](https://docs.aws.amazon.com/cli/latest/reference/dynamodb/list-tables.html) · [list-buckets](https://docs.aws.amazon.com/cli/latest/reference/s3api/list-buckets.html)

The four calls are independent of the state file. That is the point: `tofu destroy` can report success while a resource it could not delete is still there, and the only way to know is to ask the service.

The check prints one row per step, in the order the parts appear, and a step is green only when its file is in place and every assertion in it passes. A red row prints the reason underneath it, naming the file, the value, or the attribute that is wrong. ## Done when (the same day, in one sitting)

Capture first, then destroy, then confirm. Once it is gone, the numbers are gone with it.

### 1. Save what existed

```bash
tofu -chdir=terraform show -no-color > evidence/terraform-show-before-destroy.txt
wc -l evidence/terraform-show-before-destroy.txt
```

Expected: a few hundred lines. An empty file means you are in the wrong folder or the state is not the one you applied.

This file goes into a public repository, and it carries your account ID in every ARN and your address in the budget's subscriber. Both are public from the commit on. Open the file and decide that you accept it, or mark `alert_email` with `sensitive = true` in `terraform/variables.tf` before the plan that produces it, which makes the show file print `(sensitive value)` instead of the address. Editing the file before you commit is the third option, and it is the one that leaves the account ID in place.

### 2. Destroy, with the log saved

```bash
export TF_VAR_alert_email="you@example.com"
tofu -chdir=terraform destroy -auto-approve -no-color 2>&1 | tee evidence/destroy.log
```

The variable is still required: `alert_email` has no default, and `destroy` evaluates the configuration to plan the removal, so a shell without it fails before anything is destroyed. The value itself does not matter here; the budget is going away either way.

Expected, at the end: `Destroy complete! Resources: 19 destroyed.` Read the lines above it. A resource that failed to delete appears as an error, and the count is then lower than 19.

The bucket is versioned and holds `force_destroy = true`, so Terraform empties it itself. If the destroy stops on the bucket, the usual reason is an object version written after the plan started; run the destroy again, once.

### 3. Ask AWS, do not trust the log

```bash
scripts/check-destroyed.sh
```

Expected: four ✅ lines and `👍 Nothing with the prefix serverless-pipeline is left in this account.` If a line is ❌, the resource it names is still billing. Delete it by hand, note why in the decision log, and run the script again.

### 4. Leave the bootstrap stack alone

The bootstrap folder needs the same bucket name SP2 set, because its own state lives in that bucket. Export it in this shell first:

```bash
export TF_VAR_state_bucket="tfstate-$(aws sts get-caller-identity --query Account --output text)-serverless"
tofu -chdir=terraform/bootstrap plan
```

Expected: `No changes.` With the export in place, nothing in the plan mentions the state bucket. If the plan asks for a value or wants to replace the bucket, `TF_VAR_state_bucket` is unset or names a different account.

The OIDC provider and the CI role live in their own state and their own folder, and SP14 does not touch them. The state bucket stays too; it costs pennies and every later repository in this project uses it.

If that plan wants to destroy the provider or the role, you are in the wrong folder. Stop and read the plan.

### 5. Check the evidence folder

```bash
ls -la evidence
```

Expected: the show file, the destroy log, and the benchmark files from SP13. No video and no screenshots: every file in this folder is text, JSON, or a log, and nothing is larger than a few hundred kilobytes.

Merge the pull request on GitHub, then clean up the branch:

```bash

git branch -d sp14-destroy

```

`git branch -d` refuses after a squash merge, because the branch's commits are not in `main`; `git branch -D sp14-destroy` is the same delete. The remote branch is already gone: `delete_branch_on_merge` removes it when the pull request merges.
