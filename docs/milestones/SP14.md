**The money stops here.** The destroy is the last thing that touches AWS, and it
happens the same day the evidence is captured.

It also has a hard end date: the account closes on 2026-11-05. A destroy left
unconfirmed after that date cannot be confirmed at all, because the services that
answer `check-destroyed.sh` stop existing. Finish it before then.

## Goal

Two artifacts and one action. The action is the destroy. The artifacts are a
script that asks AWS whether anything is left, and an index that says what the
evidence folder holds and why each file matters.

A destroy that failed halfway is the expensive mistake in this project: the log
says it finished, one resource is still there, and it bills until somebody
notices.

## Part 1: The check

#### 1. `scripts/check-destroyed.sh`

**File Type:** `bash`
**File Name:** `scripts/check-destroyed.sh`

| Piece | Set To |
|---|---|
| strict mode | `set -euo pipefail` |
| the prefix | `PREFIX=${1:-serverless-pipeline}` |
| a helper | a function that takes a label and a found value, prints ✅ when the value is empty, prints ❌ and the value when it is not, and sets a flag |
| the four checks | Lambda functions with `--query "Functions[?starts_with(FunctionName,'$PREFIX')].FunctionName"`, SQS queues with `--queue-name-prefix "$PREFIX"`, DynamoDB tables with a `starts_with` filter on the name, and buckets with a `starts_with` filter on `Name` |
| the ending | when the flag is set, print the hint and `exit 1`; otherwise print one success line and exit `0` |

**Docs:** [list-functions](https://docs.aws.amazon.com/cli/latest/reference/lambda/list-functions.html) · [list-queues](https://docs.aws.amazon.com/cli/latest/reference/sqs/list-queues.html) · [list-tables](https://docs.aws.amazon.com/cli/latest/reference/dynamodb/list-tables.html) · [list-buckets](https://docs.aws.amazon.com/cli/latest/reference/s3api/list-buckets.html)

The four calls are independent of the state file. That is the point: `tofu
destroy` can report success while a resource it could not delete is still there,
and the only way to know is to ask the service.

## Check it

### How to see your results


The check prints one row per step, in the order the parts appear, and a step is
green only when its file is in place and every assertion in it passes. A red row
prints the reason underneath it, naming the file, the value, or the attribute
that is wrong. CI prints the same rows in the job summary, so the local run and
the remote run read identically.


**Locally:** `.github/scripts/check.sh SP14`. **On the pull request:** **Actions**,
newest run, **Summary**.

| Step | Checks |
|---|---|
| 1 (destroyed) | the four service calls, the prefix filter, and the failing exit |
| 2 (evidence) | the title and one table row per file the folder holds |

## Done when (the same day, in one sitting)

Capture first, then destroy, then confirm. Once it is gone, the numbers are gone
with it.

### 1. Save what existed

```bash
tofu -chdir=terraform show -no-color > evidence/terraform-show-before-destroy.txt
wc -l evidence/terraform-show-before-destroy.txt
```

Expected: a few hundred lines. An empty file means you are in the wrong folder or
the state is not the one you applied.

### 2. Destroy, with the log saved

```bash
tofu -chdir=terraform destroy -auto-approve -no-color 2>&1 | tee evidence/destroy.log
```

Expected, at the end: `Destroy complete! Resources: 19 destroyed.` Read the lines
above it. A resource that failed to delete appears as an error, and the count is
then lower than 19.

The bucket is versioned and holds `force_destroy = true`, so Terraform empties it
itself. If the destroy stops on the bucket, the usual reason is an object version
written after the plan started; run the destroy again, once.

### 3. Ask AWS, do not trust the log

```bash
scripts/check-destroyed.sh
```

Expected: four ✅ lines and `👍 Nothing with the prefix serverless-pipeline is
left in this account.` If a line is ❌, the resource it names is still billing.
Delete it by hand, note why in the decision log, and run the script again.

### 4. Leave the bootstrap stack alone

The bootstrap folder needs the same bucket name SP2 set, because its own state
lives in that bucket. Export it in this shell first:

```bash
export TF_VAR_state_bucket="tfstate-$(aws sts get-caller-identity --query Account --output text)-serverless"
tofu -chdir=terraform/bootstrap plan
```

Expected: `No changes.` With the export in place, nothing in the plan mentions the
state bucket. If it wants to replace the bucket, the variable is unset or names a
different account, and the plan is reading the placeholder default.

The OIDC provider and the CI role live in their own state
and their own folder, and SP14 does not touch them. The state bucket stays too;
it costs pennies and every later repo in the program uses it.

If that plan wants to destroy the provider or the role, you are in the wrong
folder. Stop and read the plan.

### 5. Check the evidence folder

```bash
ls -la evidence
```

Expected: the show file, the destroy log, and the benchmark files from SP13. No
video and no screenshots: every file in this folder is text, JSON, or a log, and
nothing is larger than a few hundred kilobytes.
