## Part 1: The redrive script

#### 1. `scripts/redrive.sh`

**File Type:** `bash`
**File Name:** `scripts/redrive.sh`

| Piece | Set To |
|---|---|
| the first line | `#!/usr/bin/env bash` |
| strict mode | `set -euo pipefail` |
| the three values | read with `tofu -chdir=terraform output -raw` for `dlq_url`, `dlq_arn`, and `main_queue_arn` |
| the count | a function that asks for `ApproximateNumberOfMessages` on the dead-letter queue and prints the value |
| the guard | if the count is `0`, print nothing to move and exit `0` |
| the move | `aws sqs start-message-move-task --source-arn "$DLQ_ARN" --destination-arn "$MAIN_ARN"` |
| the wait | `for i in $(seq 1 60)`, printing the remaining count, breaking at `0`, sleeping 2 seconds |
| the ending | after the loop, count once more. If anything is left, print the count, print the `aws sqs receive-message` line to read them, and `exit 1` |

**Docs:** [StartMessageMoveTask](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_StartMessageMoveTask.html) · [GetQueueAttributes](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/APIReference/API_GetQueueAttributes.html)

The move is asynchronous. A script that starts it and exits proves nothing; the bounded loop is what turns "I asked" into "it happened".

### 1. Apply, with the caps first

Both bundles are built here, and `npm ci` downloads their dependencies into `src/*/node_modules/`. That is an install, so approve it before the block.

```bash

(cd src/consumer && npm ci && npm run build)
```



### 2. The happy path

```bash
mkdir -p scratch
echo '{"idempotencyKey":"evt-001","payload":"hello"}' > scratch/evt-001.json
aws s3 cp scratch/evt-001.json "s3://$(tofu -chdir=terraform output -raw landing_bucket)/evt-001.json"
```

Wait for the row, in a bounded loop:

```bash
for i in $(seq 1 20); do
  rows=$(aws dynamodb scan --table-name "$(tofu -chdir=terraform output -raw table_name)" --select COUNT --query 'Count' --output text)
  echo "poll $i: $rows row(s)"
  [ "$rows" -ge 1 ] && break
  sleep 5
done
```

Expected: a count of `1` within about fifteen seconds. A count of `0` means the trigger did not fire: check the ingest function's log group, then the bucket notification.

**This is where the capture starts.** Record the screen from here to the end of step 5, with the recorder you approved in SP0 (`wf-recorder` on this machine). Waiting is most of what happens next, so record the waits and speed them up, or cut between the moments that matter: the trimmed clip is what the README links, and 60 to 90 seconds is the length of the clip, not of the sitting. The untrimmed fifteen minutes is not the asset.

### 3. The poison message

Put a body on the queue that is not JSON, which is what a broken producer sends:

```bash
aws sqs send-message \
  --queue-url "$(tofu -chdir=terraform output -raw main_queue_url)" \
  --message-body 'this is not json'
```

Watch the retries, then the dead-letter queue. The visibility timeout is 180 seconds and the limit is 5, so this takes about fifteen minutes. Every poll is bounded:

```bash
for i in $(seq 1 40); do
  main=$(aws sqs get-queue-attributes --queue-url "$(tofu -chdir=terraform output -raw main_queue_url)" --attribute-names ApproximateNumberOfMessages --query 'Attributes.ApproximateNumberOfMessages' --output text)
  dlq=$(aws sqs get-queue-attributes --queue-url "$(tofu -chdir=terraform output -raw dlq_url)" --attribute-names ApproximateNumberOfMessages --query 'Attributes.ApproximateNumberOfMessages' --output text)
  echo "poll $i: main=$main dlq=$dlq"
  [ "$dlq" -ge 1 ] && break
  sleep 30
done
```

Expected: `dlq=1` after roughly fifteen minutes, and `main=0`. The consumer's log shows five failed records with the same message id. Do not shorten the visibility timeout to make the recording easier: say in the README how long the real path takes.

### 4. Fix it, then redrive

A redrive moves a message. It does not change one. Redriving the poison message as it stands puts the same invalid body back on the queue, where it fails five more times and returns to the dead-letter queue. That proves the move task works and proves nothing about recovery. Fix the message first, then move it:

1. Take the poison out of the dead-letter queue, so the redrive has one message.
2. Send the corrected form of that event to the dead-letter queue.
3. Redrive, and watch this one succeed and write a row.

```bash
DLQ=$(tofu -chdir=terraform output -raw dlq_url)

# 1. The poison cannot be fixed by moving it, so remove it.
HANDLE=$(aws sqs receive-message --queue-url "$DLQ" --max-number-of-messages 1 \
  --query 'Messages[0].ReceiptHandle' --output text)
if [ -z "$HANDLE" ] || [ "$HANDLE" = "None" ]; then
  echo "the dead-letter queue returned no message: do not run the rest of this block; re-read step 3" >&2
else
  aws sqs delete-message --queue-url "$DLQ" --receipt-handle "$HANDLE"
  # 2. The corrected body: valid JSON with a key, which is all the consumer reads.
  aws sqs send-message --queue-url "$DLQ" \
    --message-body '{"idempotencyKey":"evt-poison"}'
fi
```

Now the redrive has a message that can succeed:

```bash
scripts/redrive.sh
```

Expected: a count line per poll ending at `0`, then the success line. The consumer's log shows one successful record instead of a failure, and the row exists:

```bash
aws dynamodb get-item --table-name "$(tofu -chdir=terraform output -raw table_name)" \
  --key '{"idempotency_key":{"S":"evt-poison"}}' \
  --query 'Item.idempotency_key.S' --output text
```

Expected: `evt-poison`. Keep the honest half in the capture: the redrive did not fix anything, the fix happened before it. What the redrive did was carry a valid message back to the queue, which is the recovery path a person uses after repairing a message in the dead-letter queue.

### 5. Two deliveries, one row

Upload the same object to the same key again. The same bytes under a different key is a different event, and would prove nothing. Note the time first: only invocations logged after this line count toward the second delivery:

```bash
start=$(($(date +%s) * 1000))
aws s3 cp scratch/evt-001.json "s3://$(tofu -chdir=terraform output -raw landing_bucket)/evt-001.json"
```

A count taken now proves nothing either, because the row from the first delivery is already there. And an empty queue proves nothing: the `cp` returns before S3 has delivered anything, so both queue attributes can read zero while the notification is still on its way. Wait for the evidence instead, which is the second invocation in the consumer's own log:

```bash
FN=$(tofu -chdir=terraform output -raw consumer_function_name)
for i in $(seq 1 40); do
  runs=$(aws logs filter-log-events --log-group-name "/aws/lambda/$FN" \
    --start-time "$start" --filter-pattern 'REPORT' \
    --query 'length(events)' --output text)
  echo "poll $i: $runs invocation(s) since the second upload"
  [ "$runs" -ge 2 ] && break
  sleep 5
done
```

Expected: `2` on the last line, within about a minute of the upload. Lambda writes one `REPORT` line per invocation, so two lines mean the same object was delivered twice. `1` means the second notification never reached the queue; `0` means nothing ran after the upload, and CloudWatch Logs reads from `start`, so a clock that is off is the first thing to check.

Then count, and read the row itself:

```bash
aws dynamodb scan --table-name "$(tofu -chdir=terraform output -raw table_name)" \
  --filter-expression 'idempotency_key = :k' \
  --expression-attribute-values '{":k":{"S":"evt-001"}}' \
  --select COUNT --query 'Count' --output text
```

Expected: `1`, after a poll line reading `2`. Two deliveries and one row is the proof: the second ran and left nothing behind. If the count is 0 or 2, stop and read the consumer log before recording anything.

Then stop the recording, trim it to the 60 to 90 second clip if you have not already, and upload that clip as a GitHub **Release** asset. Never commit video to the repository.
