## Goal

The same 1,000 events, one runtime at a time, measured the same way: from the
moment the runtime accepted the event to the moment the row was written. That is
the number that includes the queue wait, which is most of the latency and the
only part worth comparing.

Do the AWS half now, while the stack is up. After SP14 there is nothing left to
compare against.

## Part 1: The benchmark script

#### 1. `scripts/bench.sh`

**File Type:** `bash`
**File Name:** `scripts/bench.sh`

| Piece | Set To |
|---|---|
| strict mode | `set -euo pipefail` |
| the count | `COUNT=${1:-1000}` |
| the two values | the table name and the landing bucket, from `tofu -chdir=terraform output -raw` |
| the files | `mkdir -p scratch/bench evidence`, clear the old event files, then one file per event named `evt-<i>.json` holding `{"idempotencyKey":"bench-<i>"}` with the number zero-padded to four digits |
| the send | `aws s3 cp scratch/bench/ "s3://$BUCKET/bench/" --recursive --only-show-errors` |
| the wait | `for i in $(seq 1 60)`, a `--select COUNT` on the table, print the count, break when it reaches `COUNT`, sleep 5 |
| the raw data | `aws dynamodb scan --table-name "$TABLE" --output json > evidence/bench-aws-raw.json` |
| the latencies | a `jq` program that drops the millisecond part before `fromdateiso8601`, keeps it as a separate term, subtracts `landedAt` from `processed_at`, and sorts the result into `evidence/bench-aws-latencies.txt` |
| the summary | an `awk` one-liner that prints `n`, p50, and p95, saved to `evidence/bench-aws-summary.txt` and printed |

**Docs:** [jq manual](https://jqlang.github.io/jq/manual/) · [DynamoDB Scan](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_Scan.html)

Why the millisecond part is handled twice: `fromdateiso8601` rejects a timestamp
with a fractional second, and both of these timestamps carry one. Dropping it
entirely would quantize every latency to a whole second, which is the same as
throwing the measurement away.

Why a bounded wait for the rows: the events arrive faster than the consumer
writes them, and a scan taken too early measures the queue, not the pipeline.

### 2. The Compose column

Measure the Compose runtime the same way, with the stack from SP10 running. Start
from an empty table so the count means something:

```bash
podman compose exec postgres psql -U postgres -d events \
  -c 'delete from events where idempotency_key is not null'
podman compose exec redis redis-cli DEL events events-dead
```

Send 1,000 events through the ingest service. Each one is an HTTP request, so the
loop is slow on purpose and its length is fixed:

```bash
for i in $(seq 1 1000); do
  curl -s -o /dev/null -X POST http://localhost:8081/ \
    -H 'content-type: application/json' \
    -d "{\"idempotencyKey\":\"bench-$i\"}"
done
```

Wait until the worker has stored all 1,000 rows. Reading early gives a short
`n` and a p50 that measures the wait rather than the pipeline:

```bash
for i in $(seq 1 60); do
  n=$(podman compose exec -T postgres psql -U postgres -d events -t -A \
    -c "select count(*) from events where idempotency_key like 'bench-%'")
  echo "poll $i: $n row(s)"
  [ "$n" -ge 1000 ] && break
  sleep 2
done
```

Then read the two timestamps out of Postgres. `landed_at` is its own column,
written by the worker from the stream field the ingest service set, so this is
the same definition as the AWS half: the write time minus the landing time.

```bash
mkdir -p scratch
podman compose exec -T postgres psql -U postgres -d events -t -A -c \
  "select extract(epoch from (processed_at - landed_at)) from events where idempotency_key like 'bench-%' order by 1" \
  > scratch/compose-latencies.txt
```

Copy those numbers into `evidence/bench-compose-latencies.txt`, compute `n`,
`p50`, and `p95` with the same `awk` line the script uses, and save the line as
`evidence/bench-compose-summary.txt`. Note in the README that both columns come
from the same definition and the same 1,000 events.
