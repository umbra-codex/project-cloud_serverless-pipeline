## Before step 1: Podman, on this machine

The Compose runtime runs on this machine (the Kamrui H1), the host you are reading this on. The engine here is Podman 6.1.4, rootless, with `runc` as the runtime, `netavark` for networking, and overlay storage. There is no second machine, and there is no `docker` binary: every container command in this guide is `podman`, a `docker ...` command fails here because nothing provides that name, and no `podman-docker` shim is installed.

Rancher Desktop is installed and is not in this path: its engine is containerd, and this guide uses neither its containers nor its cluster. The cluster that product would give you is k3s, a systemd service; nothing here installs it, nothing here starts it, and no step in this guide depends on it, so nothing here changes its configuration.

Two rootless facts shape the file below. A rootless user cannot publish a port below 1024 by default, which is why every port here is 8080 or 8081; the unprivileged port start is a system setting, and this guide does not change it. A container's root is your own user in the user namespace, so files written into a named volume belong to that mapping, not to real root. Both are why the stack reads only this repository's files and writes only named volumes.

Check the engine before you start:

```bash
podman version
podman compose version
systemctl --user is-active podman.socket
```

`podman version` prints the client and engine versions. A connection error instead means the user service is not up: `systemctl --user start podman.socket`.

`podman compose version` can fail for a reason you have to decide. Podman hands Compose to a provider, and this machine has no `podman-compose`. Rancher Desktop left its Compose plugin binary in `~/.rd/bin`, and `podman compose` uses it if that directory is on your `PATH`. Two commands decide it, and neither installs anything:

```bash
ls ~/.rd/bin/docker-compose
PATH="$HOME/.rd/bin:$PATH" podman compose version
```

If the second line prints a version, that `PATH` prefix is the whole fix: put it in the shell that runs the stack. If the binary is not there, or the version line still reports no provider, then the remaining route is `podman-compose` from the Arch repositories — `sudo pacman -S podman-compose` — and that install is your call. This guide installs neither.

The socket line is expected to print `inactive` today. Start it if the provider you picked needs the Docker-compatible endpoint.

`podman compose config` in the Done when section settles the second question against the real file, and it is the first thing to run: the provider is proven there before anything is built.

Nothing in this milestone spends money, touches AWS, or needs the stack applied.

## Goal

The same design without AWS: Redis Streams in place of SQS, a worker in place of the consumer function, Postgres in place of DynamoDB, and an ingest service in place of the S3 trigger. The mapping's four moving parts get a direct equivalent, and every one of them is a named thing you can point at in an interview:

| AWS | Here | The property that matches |
|---|---|---|
| SQS queue | a Redis Stream | entries stay until acknowledged |
| Event source mapping | a consumer group | a group reads each entry once |
| Visibility timeout | the idle time before `XAUTOCLAIM` reclaims | an unacknowledged entry comes back |
| `maxReceiveCount` | the delivery counter in the pending list | a message stops after five tries |
| Dead-letter queue | a second stream | failures are kept where a person can read them |
| Conditional `PutItem` | `INSERT ... ON CONFLICT DO NOTHING` | a duplicate writes nothing |
| `ReportBatchItemFailures` | `XACK` per entry | one bad entry does not fail the batch |

### compose.yaml

**File Type:** `compose`
**File Name:** `compose.yaml`

| Service | Set To |
|---|---|
| `redis` | `image: redis:7-alpine`, `command` `["redis-server", "--appendonly", "yes"]`, a named volume at `/data`, `restart: unless-stopped` |
| `postgres` | `image: postgres:16-alpine`, `POSTGRES_PASSWORD_FILE` = `/run/secrets/pg_password`, `POSTGRES_DB` = `events`, a named volume at `/var/lib/postgresql/data`, `./compose/init.sql` mounted read-only into `/docker-entrypoint-initdb.d/init.sql`, the `pg_password` secret, `restart: unless-stopped` |
| `ingest` | `build: ./compose/ingest`, `ports` `["127.0.0.1:8081:8081"]`, `REDIS_URL` = `redis://redis:6379`, `depends_on: [redis]`, `restart: unless-stopped` |
| `worker` | `build: ./compose/worker`, `REDIS_URL`, `PG_HOST` = `postgres`, `PG_USER` = `postgres`, `PG_DB` = `events`, `PG_PASSWORD_FILE` = `/run/secrets/pg_password`, `depends_on: [redis, postgres]`, the `pg_password` secret, `restart: unless-stopped` |
| top-level `volumes` | `redis-data` and `pg-data` |
| top-level `secrets` | `pg_password`, with `file: ./secrets/pg_password` |

**Docs:** [Compose file reference](https://docs.docker.com/reference/compose-file/) · [Compose secrets](https://docs.docker.com/reference/compose-file/secrets/) · [postgres image](https://hub.docker.com/_/postgres)

Every published port is bound to `127.0.0.1`, never to a bare `8081:8081` and never to every interface. The stack is reachable from this machine only. SP11 puts one Cloudflare tunnel in front of it, the status route is public and the route that submits events stays behind Access. A port published on the LAN or on the tailnet would be a second way in that no test watches.

The only host paths the file reads are this repository's own `compose/init.sql` and `secrets/pg_password`. Everything the containers write is a named volume. Nothing under your home directory is mounted into a container.

Why a password file and not `POSTGRES_PASSWORD`: the postgres image reads the file form without putting the password in the environment, where `podman compose config` and any process listing would show it. The worker reads the same file, so there is one copy of the password and it is not in git.

One behavior to expect once a password is set: the image writes `host all all all scram-sha-256` into `pg_hba.conf`, so a client that reaches Postgres over TCP without the password fails with an authentication error instead of working the way an uninitialized server did. That is the second reason both services read the same file: there is no passwordless path to fall back to.

Why `restart: unless-stopped` everywhere: this is the permanent demo, so a container that dies should come back without a person at the keyboard.

**What the tags promise.** `redis:7-alpine`, `postgres:16-alpine` and `cloudflare/cloudflared:latest` float: a later `up` can pull a different patch, and `latest` can pull a different release. That is the trade in a demo that has to keep working, and the counter-move is a digest rather than a version guess. After the first pull, `podman image inspect --format '{{.Digest}}' redis:7-alpine` prints one, and the tag written as `redis@sha256:…` cannot move. Record whichever you choose in `DECISIONS.md`.

Rootless changes what that buys you after a reboot, and it is the one limit here that can quietly break the demo. With no system daemon, nothing starts the containers at boot unless your user session does. The two pieces are `loginctl enable-linger $USER`, so the user session exists without a login, and the `podman-restart` user unit, which starts containers that carry a restart policy. Check both, and treat the install as your call:

```bash
loginctl show-user "$USER" --property=Linger
systemctl --user is-enabled podman-restart.service
```

Unverified here, because this machine's `podman.socket` is inactive and no container has been run: whether these two are enough on Podman 6.1.4, and whether your compose provider writes the restart policy in a form `podman-restart` picks up. Prove it with one reboot before you call the demo permanent: after the reboot, `podman ps` should list the five services, and `podman compose ps` should agree.

### compose/init.sql

**File Type:** `sql`
**File Name:** `compose/init.sql`

| Statement | Set To |
|---|---|
| the table | a table statement for `events` that does nothing when the table is there, with four columns: `idempotency_key TEXT PRIMARY KEY`, `payload JSONB NOT NULL`, `landed_at TIMESTAMPTZ NOT NULL`, `processed_at TIMESTAMPTZ NOT NULL DEFAULT now()` |

**Docs:** [Table statements](https://www.postgresql.org/docs/current/sql-createtable.html) · [PostgreSQL INSERT statement](https://www.postgresql.org/docs/current/sql-insert.html)

The guarantee lives in the schema, not in the application. `ON CONFLICT DO NOTHING` only does the right thing because the key is the primary key; without that, a duplicate inserts a second row and the demo quietly stops matching the AWS side.

`landed_at` is not decoration either. The worker writes it on every row, and the benchmark's latency is `processed_at - landed_at`. If a Postgres volume from an earlier attempt already exists, the entrypoint never runs `init.sql` again on it, so the table stays at whatever it was created with and step 4 stays red. When the volume predates this file, recreate it once with `podman compose down -v` before you start the stack again. That deletes the demo's rows, which is the point.

Also add `secrets/` to `.gitignore` in this milestone. The folder holds the database password, and a password file in git is a password in git forever.

## Part 2: The worker

### compose/worker/

Four files: `index.ts`, `package.json`, `tsconfig.json`, `Dockerfile`.

#### 2. `compose/worker/index.ts`

**File Type:** `typescript`
**File Name:** `compose/worker/index.ts`

Settings at the top of the file:

| Name | Set To |
|---|---|
| `WORKER_ID` | `process.env.WORKER_ID`, with a fallback of `worker-` plus the process id |
| `MAX_DELIVERIES` | `5` |
| `CLAIM_IDLE_MS` | `30000` |
| `BATCH` | `10` |

Behavior, once at startup, then in a loop:

1. Connect to Redis at `REDIS_URL` and build a Postgres pool from `PG_HOST`, `PG_USER`, `PG_DB`, and the password read from `PG_PASSWORD_FILE` and trimmed.
2. Call `xGroupCreate("events", "workers", "0", { MKSTREAM: true })` once, and swallow the `BUSYGROUP` error, which is what a restart produces.
3. In each pass: `xAutoClaim("events", "workers", WORKER_ID, CLAIM_IDLE_MS, "0", { COUNT: BATCH })`, then `xReadGroup("workers", WORKER_ID, [{ key: "events", id: ">" }], { COUNT: BATCH, BLOCK: 5000 })`.
4. For each entry from either call, skip a null entry (a claimed id whose payload was trimmed comes back null) and then:
   - insert one row into `events` with `idempotency_key`, `payload`, and `landed_at` from the entry, ignoring a conflict. `landedAt` arrives as an ISO string on a stream field, so cast it with `::timestamptz`, which is the column type the schema declares;
   - on success, `xAck("events", "workers", msg.id)`;
   - on error, `xPendingRange("events", "workers", msg.id, msg.id, 1)`, read `deliveriesCounter` from the first result, and when it is 5 or more, `xAdd("events-dead", "*", msg.message)` and then `xAck`.
5. Otherwise leave the message pending. The next pass's `XAUTOCLAIM` picks it up.

The loop variable in those three calls is `msg`, which is the name the reference build uses; the check accepts any identifier, so `entry` works too as long as one name is used throughout.

**Docs:** [XAUTOCLAIM](https://redis.io/docs/latest/commands/xautoclaim/) · [XREADGROUP](https://redis.io/docs/latest/commands/xreadgroup/) · [XACK](https://redis.io/docs/latest/commands/xack/) · [XPENDING](https://redis.io/docs/latest/commands/xpending/) · [ON CONFLICT](https://www.postgresql.org/docs/current/sql-insert.html)

The two-argument summary form of `XPENDING` returns totals only. A retry limit built on it never triggers, because there is no per-message count to compare with 5. That is why the ranged form is in the step table.

#### 3. The other three files

| File | Set To |
|---|---|
| `package.json` | `name` `"worker"`, `private` true, `type` `"module"`, `scripts.build` `"tsc"`, dependencies `pg` `^8.0.0` and `redis` `^5.0.0`, devDependencies `@types/node` and `typescript` |
| `tsconfig.json` | `target` `"ES2022"`, `module` `"NodeNext"`, `moduleResolution` `"NodeNext"`, `outDir` `"dist"`, `strict` true, `esModuleInterop` true, `skipLibCheck` true, `noImplicitAny` false, `include` `["index.ts"]` |
| `Dockerfile` | `FROM node:24-alpine`, workdir `/app`, copy the package files, `npm install`, copy the rest, `npm run build`, `USER node`, `CMD` `["node", "dist/index.js"]` |

`npm install`, not `npm ci`, in these three folders: the compose services carry a `package.json` and no lock file, and `npm ci` refuses to run without one. The Lambda folders are the opposite, because SP6 and SP7 have you commit a lock and CI builds them with `npm ci`. If you would rather the images resolve from a lock, run `npm install` in the folder, commit the `package-lock.json`, and change the Dockerfile line to `npm ci`; that is a sixth file per service and your call.

**Two files the build context wants.** Add `compose/ingest/.dockerignore` and `compose/worker/.dockerignore`, each with two lines, `node_modules` and `dist`; SP11 adds the same file for the status service. Without them every `up --build` copies the host's `node_modules` into the image before the build step overwrites it: slow, and a way for a local file to reach an image.

`noImplicitAny` is off because `pg` ships no type declarations of its own, so `@types/pg` would be a fifth dependency in a folder whose code is read by the text check rather than compiled here. Add it and turn the flag on if you want the compiler in the loop; until then the worker's shapes are proven by step 2 and by the forced failure below, not by `tsc`.

`USER node` is not decoration. The worker, the ingest service, and the status service each run as the image's non-root user, so a bug in a handler cannot write to the host as you. The build stage is root, the running container is not.

One Podman difference in the build: Podman defaults to the OCI image format, and `HEALTHCHECK` is a Docker-format instruction with no OCI field, so a `HEALTHCHECK` in these Dockerfiles would be dropped without an error. None of the three has one, and nothing below depends on a health status. If you add one, build with `podman build --format docker` and read it back with `podman inspect --format '{{.Config.Healthcheck}}' <image>`. That format default is the one thing here worth confirming on your machine before you rely on it.

## Part 3: The ingest service

### compose/ingest/

#### 4. `compose/ingest/index.ts`

**File Type:** `typescript`
**File Name:** `compose/ingest/index.ts`

| Behavior | Set To |
|---|---|
| the server | `createServer` on port `8081` |
| a method that is not POST | answer `405` and stop |
| the body | read the request stream as text, then parse it as JSON. A body that does not parse, or one without a string `idempotencyKey`, gets `400` and stops |
| the stream entry | `xAdd("events", "*", { idempotencyKey: body.idempotencyKey, payload: raw, landedAt: new Date().toISOString() })`, with the key as it arrived |
| the response | `202` and no body when the event is queued, `400` when it is rejected |

The other three files are the worker's, with the package name `ingest`, one dependency (`redis`), and the same Dockerfile.

**Docs:** [Node HTTP server](https://nodejs.org/api/http.html) · [XADD](https://redis.io/docs/latest/commands/xadd/)

`202`, not `200`: the request is queued, not processed. `landedAt` is stamped here for the same reason the Lambda stamps it from the event: the benchmark's clock starts when the runtime accepts the event.

`String(body.idempotencyKey)` is what this replaces: a body without the field becomes the literal `"undefined"`, every such event collapses onto one row, and the service still answers `202`. Rejecting it is what stops an unkeyed event from looking processed.

### About step 5

Step 5 is an absence check with a precise meaning: `secrets/pg_password` must never be committed. In a real clone the check asks git whether the path is tracked, so writing the file on this machine and leaving it gitignored keeps the row green, which is what the Done when below does. It is green from the start and it stays green until someone commits the file, and then it is red until the password is rotated and the file is removed from the index. It does not turn green when you build something; it is a rule, not a step.

### About step 6

Step 6 is the isolation guard. It reads the compose file and the two Dockerfiles and fails on the shapes this milestone exists to avoid: a port published on anything but `127.0.0.1`, a binding on every interface, a host path under a home directory, a privileged container, a `user: root`, or a Dockerfile that ends without `USER node`. It turns ✅ with step 3, when the second Dockerfile exists, and every later milestone's check re-runs it, so an edit that opens a port fails here instead of on the network.

## Done when (on this machine, the Kamrui H1)

Everything here runs on this machine (the Kamrui H1), in one terminal, from the repo root. It uses the Podman you checked at the top of this brief.

```bash
mkdir -p secrets
printf '%s' 'a-long-password' > secrets/pg_password
podman compose config
```

Expected: `podman compose config` prints the resolved file with no error. A missing secret file is the usual failure, and the message names the path. A "no compose provider" message here is the engine check from the top of the brief, not a problem with the file.

```bash
podman compose up -d --build
podman compose ps
```

Expected: redis, postgres, ingest, and worker are running. `podman compose ps` prints state rather than Docker's health column, so readiness is what the count loop below measures, not a green word here. The first build takes a few minutes.

Send one event and check both ends:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:8081/ \
  -H 'content-type: application/json' \
  -d '{"idempotencyKey":"sp10-1","payload":"hello"}'
podman compose exec redis redis-cli XLEN events
for i in $(seq 1 12); do
  n=$(podman compose exec -T postgres psql -U postgres -d events -t -A -c 'select count(*) from events')
  echo "poll $i: $n row(s)"
  [ "$n" -ge 1 ] && break
  sleep 2
done
```

Expected: `202`, then `1` on the stream, then a count that reaches `1` within about ten seconds. The worker blocks for 5,000 milliseconds on each read, so the first seconds can legitimately show `0`; the loop is what turns that wait into a result. A loop that finishes at `0` is the real failure: check `podman compose logs worker` for a connection error, and check that the consumer group was made.

The port is published on loopback, so `http://127.0.0.1:8081/` answers here and this machine's LAN address does not. Nothing outside this machine can submit an event until SP11 adds the tunnel, and that route stays behind Access.

Send the same event twice and confirm the count does not move:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:8081/ \
  -H 'content-type: application/json' \
  -d '{"idempotencyKey":"sp10-1","payload":"hello"}'
podman compose exec postgres psql -U postgres -d events -c 'select count(*) from events'
```

Expected: `202` and a count of `1`. Two deliveries, one row.

Now force the failure path, because this milestone builds it and nothing so far has made it fire. Stop the database, send one event, and watch it run out of retries into `events-dead`. The worker blocks for 5,000 milliseconds per read and reclaims a pending entry after 30 idle seconds, so five attempts take about two and a half minutes. Every poll is bounded:

```bash
podman compose stop postgres
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://localhost:8081/ \
  -H 'content-type: application/json' \
  -d '{"idempotencyKey":"sp10-fail","payload":"forced"}'
for i in $(seq 1 40); do
  dead=$(podman compose exec -T redis redis-cli XLEN events-dead)
  echo "poll $i: $dead in the dead-letter stream"
  [ "$dead" -ge 1 ] && break
  sleep 5
done
```

Expected: `202` from the request, then `0` until about the fifth attempt and `1` after it. A stream that never fills means the retry limit is not firing: check `MAX_DELIVERIES` and the ranged `XPENDING` call from step 2.

Then repair and requeue by hand, which is the job `scripts/redrive.sh` automates in SP12. Read the entry out of the dead stream first:

```bash
podman compose start postgres
podman compose exec redis redis-cli XRANGE events-dead - +
```

Copy its id and its three fields, send them back to the live stream, and confirm one row lands:

```bash
podman compose exec redis redis-cli XADD events '*' \
  idempotencyKey sp10-fail \
  payload '{"idempotencyKey":"sp10-fail","payload":"forced"}' \
  landedAt "$(date -u +%Y-%m-%dT%H:%M:%S.000Z)"
podman compose exec -T postgres psql -U postgres -d events -t -A \
  -c "select count(*) from events where idempotency_key = 'sp10-fail'"
```

Then drop the dead entry and watch the depth the status page reports return to 0. Copy the id from the `XRANGE` output into the first line:

```bash
DEAD_ID='paste-the-id-from-XRANGE'
podman compose exec redis redis-cli XDEL events-dead "$DEAD_ID"
podman compose exec redis redis-cli XLEN events-dead
```

Expected: `1` for the row, then `0` for the stream length. If the row does not appear, the requeued entry is missing a field the worker reads; compare it with the `XADD` the ingest service performs.

Leave the stack running. SP11 publishes it through a tunnel that starts on this machine; until then nothing is exposed. The stack now holds one real row and an empty dead-letter stream, so the status page has something to report in SP11.

This reads the milestone check only: the `static` and `plan` jobs your `ci.yml` runs are separate required checks, and the pull request's **Checks** tab is where a red one shows.

When it prints `👍 SP10 passed.`, retitle the pull request and mark it ready:

```bash
gh pr edit --title "feat(sp10): run the same pipeline with Redis, a worker, and Postgres"
gh pr ready
```

Paste the three command outputs into the pull request body.

## After the merge

Merge the pull request on GitHub, then clean up the branch:

```bash
git switch main && git pull
git branch -d sp10-compose
git fetch --prune
```

`git branch -d` refuses after a squash merge, because the branch's commits are not in `main`; `git branch -D sp10-compose` is the same delete. The remote branch is already gone: `delete_branch_on_merge` removes it when the pull request merges.
